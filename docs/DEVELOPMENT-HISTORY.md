# How Continuity reached Core 0.2

The project grew through small demonstrations of a security investigation that outlives its original software worker.

| Stage | What it added |
| --- | --- |
| Core 0.1 | Rule-based permission decisions, saved event history, receipts and unfinished duties that survive a replacement. |
| Core 0.2 | A common engine and explicit acknowledgments from the components carrying out operations. |
| Operator workflow | Saved progress, handover, permission revocation, reporting-key replacement and recovery from local records. |
| Public evaluation | A runnable practice investigation, a visual demo and recorded Linux examples. |
| Verification and reader | Reproducible checks and a read-only interface for asking what the supplied history establishes. |
| Easier setup and developer package | A Node-only recorded example, fresh tutorial cases and a JavaScript package with TypeScript declarations and a separate integration example. |

[Try the tutorial](TUTORIAL.md), [inspect the code](DEVELOPER.md), or [read what has been tested](../VALIDATION.md). Local demonstrations do not establish production safety.

## What comes next is a discussion

Use the [public RFC process](RFC.md) to propose changes. Operating-system enforcement, longer-lived agents and privacy techniques such as zero-knowledge proofs are possible research directions, not features promised by this release.

The practical priorities remain: keep identity, execution, permission and unfinished work separate; preserve revocations and unresolved outcomes during recovery; and check every protected operation through a trusted component.
