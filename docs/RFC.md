# Propose a change

Continuity welcomes questions, issues, forks and pull requests. Small documentation changes, tests and focused fixes can go straight to a pull request. For a proposed change to protocol behavior, a public interface, a security boundary or compatibility, start a GitHub issue or draft pull request titled `RFC: <short proposal>`. Existing code can accompany the proposal; discussion may change its shape.

Keep the proposal short. Describe the problem and a concrete use case, the behavior you want, alternatives considered, compatibility or migration effects, security and privacy implications, and how someone could test the result. A sketch or minimal example is enough to begin; questions and incomplete ideas are welcome.

Report vulnerabilities and sensitive exploit details through the repository's private Security reporting path. A public RFC can follow when disclosure is safe.

Anyone may comment or propose revisions. Maintainers will summarize the discussion and record the RFC as **accepted**, **needs revision**, **deferred** or **declined**, with a public reason. There is no fixed voting threshold or promise that silence means consent. An accepted RFC establishes direction for the upstream project; it does not merge code or make an evaluation build production-ready. Implementation still needs a reviewable pull request, tests and an updated versioned contract or decision record where behavior changes.

The published source, reference contracts, tests, security boundaries and license describe the current upstream edition. This RFC process lets those materials evolve in public. Forks may make different choices under the applicable licenses; an upstream decision does not govern them.
